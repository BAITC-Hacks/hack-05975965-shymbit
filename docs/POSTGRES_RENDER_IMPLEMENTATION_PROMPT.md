## 1. Цель и границы

Ты дорабатываешь AI Sana Challenge Hub — React/TypeScript frontend и Node.js/Express backend. Заменить файловое хранение в рабочем окружении на PostgreSQL так, чтобы задачи, команды, отклики, отзывы и AI-планы сохранялись независимо от перезапуска, сна или повторного развёртывания приложения на Render.

Этот файл — готовый промпт для следующей задачи. Его создание не означает разрешения прямо сейчас создавать облачные ресурсы, оплачивать услуги, импортировать настоящие данные или публиковать приложение.

При реализации:

- Сохрани API-контракты, текущий интерфейс, AI-адаптер и архитектуру без масштабного переписывания.
- Предпочитай минимальную PostgreSQL-интеграцию через `pg` и версионированные SQL-миграции; не добавляй ORM без необходимости.
- Оставь JSON-адаптер для локальной разработки и существующих тестов, но запрети его незаметное использование в production.
- Не удаляй исходный JSON, не включай пользовательские данные и секреты в Git.

## 3. Ограничения Render, которые нельзя скрывать

Файловая система Web Service временная: локальный `db.json` не является постоянным хранилищем при перезапусках и deploy. Бесплатный Web Service не поддерживает постоянный диск. Бесплатная Render Postgres истекает через 30 дней; это вариант проверки, а не бессрочного хранения. См. [официальные ограничения](https://render.com/docs/free).

Поэтому основная долгосрочная конфигурация — Render Postgres на согласованном платном тарифе. Если бюджет нулевой, остановись перед созданием ресурсов и согласуй внешнюю PostgreSQL, заново проверив её актуальные ограничения. Не обещай бесплатное бессрочное хранение и не организуй обход сроков жизни бесплатных баз.

Сохранность при рестарте приложения не означает защиту от удаления БД, истечения тарифа, неоплаты или ошибочных изменений. Для этого нужны резервные копии и проверяемое восстановление.

## 5. Сохранить существующую бизнес-логику

- Публикация доступна из любого неопубликованного статуса после `confirm: true`. Порог готовности 75 не возвращать как блокировку.
- Повторная публикация уже опубликованной задачи сохраняет дату и не создаёт копию.
- Архив скрыт из каталога. `/restore` возвращает задачу для редактирования, не публикуя её автоматически; `/publish` может публиковать напрямую из архива.
- Карточка, ответы, отклики и планы сохраняются при архивировании/восстановлении.
- Каталог по умолчанию выдаёт только опубликованные задачи, новые первыми; `status=all` нужен существующему интерфейсу.
- Сохрани фильтры, форму `{ items, total }`, camelCase, значения `null`/пустых массивов и ISO-даты.
- Несколько команд могут получить принятые отклики. `teamId` в отклике необязателен: остаются отклики без профиля.
- Отзыв допустим после принятого отклика этой команды на задачу. Повторный отзыв одного нормализованного автора по той же паре запрещён.
- Рейтинг команды: среднее с округлением до одного знака и число отзывов.
- Запоздавшая генерация AI не должна отменять публикацию, архивирование или более свежие правки; конфликт возвращает `409`.
- Не добавляй автоматические повторные платные AI-запросы при сбоях БД.

## 6. Интерфейс хранилища и выбор адаптера

Создай `createPostgresStore` с тем же асинхронным интерфейсом, что у `createJsonStore`:

```text
createTask, listTasks, getTask, updateTask
createApplication, listApplications, getApplication, updateApplication
createTeam, listTeams, getTeam, updateTeam
listReviews, createReview, hasAcceptedApplication, hasApplicationReview
createAssistantPlan, listAssistantPlans, getAssistantPlan
```

Особенно сохрани `updateTask(id, patch, expectedTask)`:

- `patch` — объект либо синхронная функция от актуальной копии задачи.
- `null` от функции означает отсутствие изменений, без обновления `updatedAt`.
- Несовпадение `expectedTask` с текущим снимком вызывает `409`.
- Отсутствующая запись возвращает `null`, дублирующий отзыв — `null`, как в текущем адаптере.

Предлагаемый выбор режима:

1. `STORAGE_DRIVER=postgres` требует `DATABASE_URL` и успешного подключения; при ошибке старт завершается с ненулевым кодом.
2. `STORAGE_DRIVER=json` разрешён только вне production.
3. Без явного драйвера наличие `DATABASE_URL` выбирает PostgreSQL; отсутствие URL вне production сохраняет локальный JSON-режим.
4. В `NODE_ENV=production` отсутствие корректной PostgreSQL-конфигурации — ошибка, а не пустой JSON-файл.

Добавь единый `close()`/`checkHealth()` у адаптеров либо равноценную абстракцию. Не загружай всю PostgreSQL-базу в процесс с последующей перезаписью целиком: изменения должны выполняться над нужными строками.

## 7. Схема PostgreSQL

Минимальная схема, уточняемая по фактическим полям кода:

| Таблица | Поля и ограничения |
| --- | --- |
| `tasks` | UUID PK; поля черновика; `skills`/`technologies`; статус с CHECK; `clarification_questions` JSONB; `card` JSONB nullable; готовность 0–100 и объяснение; даты создания/обновления/публикации |
| `teams` | UUID PK; название, описание; участники, навыки, технологии, проекты и GitHub-ссылки в JSONB/массивах; даты |
| `applications` | UUID PK; обязательный FK задачи; необязательный FK команды; снимок названия, участников и технологий; решение, контакт, комментарий, статус с CHECK; даты |
| `reviews` | UUID PK; FK задачи и команды; имя автора и отдельное нормализованное имя; оценка 1–5; текст, дата; UNIQUE по команде, задаче и нормализованному автору |
| `assistant_plans` | UUID PK; FK задачи и команды; полный проверенный план JSONB; дата |
| `schema_migrations` | идентификатор миграции, контрольная сумма, время применения |

Вложенные AI-структуры и упорядоченные списки удобно хранить в JSONB; связанные сущности — отдельными строками с внешними ключами. Не складывай все коллекции в единственный JSONB-документ.

Используй `timestamptz`, UUID и индексы: задачи по статусу/дате публикации; отклики по taskId и по паре taskId/teamId со статусом; отзывы по teamId; планы по taskId/teamId/createdAt. Ограничения удаления — `RESTRICT` по умолчанию: архив не является удалением.

Рейтинг предпочтительно вычислять из отзывов при чтении, без отдельного изменяемого счётчика. Если хранить агрегат, обновлять его в той же транзакции с блокировкой команды. API в любом случае возвращает прежний объект `rating`.

Сопоставляй SQL snake_case с API camelCase явно. Нормализуй SQL `numeric`/`count` в числа и даты в ISO, отсутствующий профиль в прежнюю семантику. Не допускай потерь пустых значений или изменения порядка участников.

## 8. Транзакции и конкурентные запросы

- Все SQL-параметры передавай параметризованно; имена изменяемых полей выбирай по белому списку.
- `updateTask`: транзакция, чтение строки с `FOR UPDATE`, восстановление API-снимка, сравнение с `expectedTask`, применение функции/объекта, UPDATE, COMMIT. Порядок ключей JSON не должен создавать ложные конфликты.
- При необходимости добавь монотонную внутреннюю версию для строгого обнаружения изменений. Не используй только время в миллисекундах как надёжную версию.
- AI вызывается до короткой транзакции: нельзя держать соединение и блокировку во время сетевого ожидания модели.
- Публикация и восстановление проверяют актуальное состояние внутри транзакции, а не только прочитанную раньше задачу.
- Создание отзыва повторно проверяет принятый отклик внутри той же транзакции. Согласуй порядок блокировок с изменением статуса отклика; защищай уникальность ограничением БД, а не одним предварительным SELECT.
- Для отправки отклика и сохранения плана повторно проверяй допустимое состояние задачи при записи, исключая гонку с архивированием. В частности, за время AI-запроса задача может уйти в архив.
- Транзакция выполняется на одном выделенном клиенте пула: `BEGIN` → операции → `COMMIT`, при ошибке `ROLLBACK`, `release()` в `finally`.
- Настрой ограниченный пул и таймауты подключения/запросов/блокировок, обработай ошибки простаивающих соединений. Не создавай новый Pool на каждый HTTP-запрос.
- Ошибки SQL, строки подключения, пароли, контакты и содержимое пользовательских запросов не должны попадать в публичные ответы или сырые логи. Введи безопасное сопоставление ошибок в `400/404/409/503`.

Основа для реализации транзакций: [node-postgres](https://node-postgres.com/features/transactions).

## 9. Миграции

- Создай `backend/migrations/` и команду `npm --prefix backend run db:migrate`.
- Повторный запуск применяет только новые миграции, проверяет контрольные суммы и не удаляет данные.
- Используй отдельный выделенный клиент и PostgreSQL advisory lock на весь запуск миграций, чтобы два сервиса не применяли их одновременно. Блокировка должна гарантированно освобождаться.
- Для транзакционных миграций записывай отметку о выполнении в той же транзакции. Ошибка останавливает запуск; частичная схема не считается успешной миграцией.
- Не выполняй разрушительные `reset`, `drop`, `truncate` и автоматический seed в production.
- Изменения должны быть совместимы с предыдущей версией приложения на время развёртывания. Откат кода не равен откату базы.
- Не выполняй миграции в build-команде frontend. Предусмотри отдельную команду и порядок запуска, описанный ниже.

## 10. Перенос существующего JSON

Создай отдельную команду импорта, например:

```powershell
npm --prefix backend run db:import-json -- --file "C:/путь/к/копии/db.json" --dry-run
npm --prefix backend run db:import-json -- --file "C:/путь/к/копии/db.json" --apply
```

Это будущие команды: сейчас в проекте они отсутствуют. Требования к реализации:

1. Без `--apply` — только проверка файла; запись невозможна по умолчанию.
2. Перед переносом остановить записи в старое приложение и сделать копию JSON вне репозитория. Получить согласие на конкретную целевую БД.
3. Валидировать исходную схему, ID, даты, статусы и связи; старые отсутствующие коллекции считать пустыми. Повреждённые записи не пропускать молча: завершить с понятным отчётом.
4. Сохранить исходные ID, даты, ответы, карточки, отклики, отзывы и историю планов. Рейтинг пересчитать из отзывов.
5. Импортировать в правильном порядке внешних ключей в одной транзакции для размера текущего MVP.
6. Повторный импорт идентичных записей безопасен; конфликт с изменённой целевой записью — остановка и откат, а не перезапись. Не использовать безусловный UPSERT поверх новых данных.
7. Вывести только число записей по сущностям и результат проверки; не печатать секреты или персональные данные.
8. Проверить API после импорта и сравнить количество/содержимое записей. Исходный файл не удалять.
9. Не запускать импорт при каждом старте или deploy. Не загружать JSON в Git для переноса.
10. После включения PostgreSQL не возвращаться к старому JSON как к актуальному источнику: новые записи уже могут быть только в БД.

## 11. Окружение и безопасность подключения

Добавь в `.env.example` только пустые или вымышленные значения:

```env
STORAGE_DRIVER=postgres
DATABASE_URL=
DB_POOL_MAX=5
DB_CONNECT_TIMEOUT_MS=5000
DB_STATEMENT_TIMEOUT_MS=10000
```

Это предлагаемые новые параметры, их обработку ещё предстоит реализовать. Сохрани `DB_FILE` для локального JSON-режима. Не делай копирование шаблона причиной поломки существующего простого запуска: документируй, какой режим выбирает локальный шаблон.

TLS задавай осознанно для конкретного маршрута подключения. Внутренний адрес Render предназначен для сервисов того же аккаунта/региона; с компьютера разработчика используется внешний адрес. У внешнего подключения обязателен TLS. Внутренние TLS-сертификаты имеют особые условия проверки, указанные Render. Не вводи глобальное отключение проверки сертификатов для всех провайдеров; проверь взаимодействие параметров URL и `ssl` в `pg`. См. [подключение Render](https://render.com/docs/postgresql-creating-connecting) и [TLS в node-postgres](https://node-postgres.com/features/ssl).

Никогда не передавай `DATABASE_URL` во frontend, в `VITE_*`, в JSON API или журнал команды. Не сохраняй настоящие URL в `render.yaml`. Используй серверные секреты Render и по возможности ограничь внешний доступ к БД.

## 12. Конфигурация Render

Подготовь документацию и при реализации — проверенный шаблон `render.yaml` без настоящих секретов. Создавать ресурсы по нему только после выбора тарифов владельцем. Точные названия тарифов и YAML-поля заново проверь в [Blueprint specification](https://render.com/docs/blueprint-spec), не угадывай.

Настройки backend:

- Root Directory: `backend`.
- Build Command: `npm ci`.
- Start Command: `npm start`, если миграции вынесены отдельно.
- `NODE_ENV=production`, `STORAGE_DRIVER=postgres`, серверные AI-параметры и `DATABASE_URL`.
- Привязка к `0.0.0.0` и `process.env.PORT`; не использовать локальный скрипт `npm run dev` в production.
- Фиксированная совместимая версия Node.js; проверить package engines и lock-файлы.
- Успешное подключение и проверка схемы до готовности сервиса обслуживать запросы.

Render предоставляет pre-deploy command для платных Web Services: туда можно поместить `npm run db:migrate`. Если выбранный сервис не поддерживает этот шаг, предусмотреть `npm run db:migrate && npm start` как Start Command с защитой миграций advisory lock и понятным завершением при ошибке. Не настраивать оба пути одновременно. См. [этапы deploy](https://render.com/docs/deploys) и [порты сервиса](https://render.com/docs/web-services).

Сохрани существующий `/health` с `service: ai-sana-challenge-hub`, от которого зависит локальный launcher. Добавь `/ready` с быстрой проверкой БД и ответом `503` при недоступности, без деталей подключения; используй его для проверки готовности Render. На `SIGTERM` перестань принимать запросы, дождись текущих в ограниченный срок и закрой Pool.

Настройки frontend:

- Root Directory: `frontend`, Build Command: `npm ci && npm run build`, Publish Directory: `dist`.
- `VITE_API_URL` — публичный HTTPS-адрес backend, `VITE_USE_MOCK_API=false` на этапе сборки.
- Настроить SPA rewrite на `index.html`; проверить прямое открытие `/my-tasks` и `/tasks/:id`.
- Ограничить CORS разрешёнными адресами через серверную настройку, сохранив локальную разработку. CORS не заменяет авторизацию.

Для импорта извне используйте внешний URL с TLS и ограниченным доступом. Не рассчитывай на SSH/shell бесплатного Web Service; не выставляй публичный HTTP-endpoint для импорта или запуска SQL.

## 13. Резервные копии и восстановление

Платная Render Postgres предоставляет возможности восстановления и экспорта; у бесплатной нет управляемого восстановления, но можно делать собственный `pg_dump`. Проверь условия выбранного тарифа и опиши отдельное хранение копий вне сервиса. См. [резервные копии Render](https://render.com/docs/postgresql-backups).

Подготовь инструкцию ручного резервирования и восстановления без паролей в истории команд. Согласуй периодичность и срок хранения; не создавай платный cron/job автоматически. Восстанавливай тестовую копию в отдельную пустую БД, а не поверх рабочей. Проверь таблицы, количество записей и сценарий API; только затем согласовывай переключение `DATABASE_URL`.

Без проверенного восстановления нельзя заявлять, что проблема потери данных решена полностью.

## 14. Тесты и критерии приёмки

Сначала прогон существующих проверок, затем общие контрактные сценарии для обоих адаптеров и отдельные интеграционные тесты на **настоящей тестовой PostgreSQL**, а не только mock.

Базовые команды, уже существующие в проекте:

```powershell
npm --prefix backend test
npm --prefix frontend test
npm run test:startup
npm --prefix frontend run lint
npm --prefix frontend run build
```

Добавить `npm --prefix backend run test:postgres` и явный `TEST_DATABASE_URL`. Изолировать данные отдельной тестовой схемой/БД со случайным именем; удалять только созданный тестом namespace. Не использовать production URL и не очищать схему `public`. PostgreSQL-команда обязана завершаться ошибкой при отсутствии тестовой БД, а не выдавать фиктивный успех; обычные локальные тесты могут оставаться JSON-only. CI должен иметь обязательный PostgreSQL job.

Проверить:

- Создание и обновление всех пяти видов сущностей, точное соответствие API-контрактов, nullable `teamId`, даты и рейтинг.
- Запись → закрытие пула/процесса → новый процесс с тем же URL → чтение тех же записей.
- Миграции на пустой БД, повторный запуск, ошибка миграции, конкурентный запуск двух миграторов.
- Импорт JSON: dry-run, сохранение ID/дат/ответов, повтор, конфликт, неправильные связи и полный откат.
- Каталог, фильтры, ручная публикация без AI, архив/restore, сохранность откликов/планов.
- Параллельная публикация одной задачи не меняет уже установленную дату и не создаёт дубли.
- Два независимых экземпляра PostgreSQL-адаптера: конкурентные правки, два отзыва одного автора, корректность рейтинга.
- Долгий ответ AI конфликтует с новыми правками/архивом, а не перезаписывает их.
- При недоступности БД нет fallback на JSON, секреты не попадают в ошибки, readiness отвечает `503`.
- Остановка сервера закрывает пул; настройки не ломают единый локальный `npm run dev`.
- Интеграционный frontend-сценарий проходит с PostgreSQL; UI-код меняется только при обоснованной необходимости.

После разрешённого deploy вручную: создать тестовую задачу и команду → отклик → план с тестовым/согласованным AI → перезапуск Web Service → чтение → redeploy → чтение. Проверить восстановление резервной копии отдельно. Без доступа к Render честно указать, что облачный рестарт ещё не проверен.

## 15. Порядок реализации и ожидаемые файлы
